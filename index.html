Make automation stop with evidence

A structured field-practice record for automation that knows when success is proven — and when execution must stop.

Replies
0
Evidence
Method note
Updated
27 Oct 2026
WJ WENJIN Editors Hermes field practice

This record is an editorial synthesis of Hermes execution and acceptance discipline. It contains no production statistics and does not present a method description as universal proof.

The complete workflow

Goal
Define the final artifact and its acceptance conditions first. “Run on schedule” is not a goal; a dated brief with required sections, source state, and a verified delivery path is.
Trigger
Scheduled and manual runs use the same entry point with an explicit run date or run ID. Acquire a lock before starting so two instances cannot write the same artifact.
Execution
Persist input snapshots, stage logs, and state. Write a temporary artifact first, validate it, then atomically replace the formal result so a partial run cannot overwrite the last usable output.
Verification
Check exit status, state file, artifact presence, content date, required structure, and final-path read-back together. “Message sent” proves transport, not that the recipient received the correct content.
Failure handling
Preserve the input, log, failed stage, and raw error. Retry only bounded, idempotent stages known to be transient. Do not silently switch sources or relabel an old artifact as the new one.
Stop conditions
Stop as blocked when required input remains stale, structure validation keeps failing, the same error repeats, the delivery window has passed, or the next step requires human judgment. Stopping is part of the workflow.

Evidence to retain

  • Trigger configuration and the actual run entry point
  • Run ID, starting state, and exit state
  • Input snapshot or traceable source locator
  • The verifier’s raw output
  • Final artifact path and read-back result

This example includes no production logs, so it is not labeled directly reproducible.

Reproduction path

  1. Choose one scheduled task; define its artifact and acceptance conditions.
  2. Route scheduled and manual runs through the same entry point and fix a run ID.
  3. Add a state file and temporary artifact, then use atomic replacement.
  4. Force a missing-input failure and confirm the previous output remains intact.
  5. Repeat the same run ID and check for duplicate side effects.

Limits

This is a reliability pattern, not a drop-in script. Locking, state files, atomic replacement, and alerting depend on the operating system and runtime platform.

The record makes no quantified claim about runtime, success rate, or cost savings, and does not claim suitability for every automation task.

Editorial sample

Read browser state before taking action

A record structure that separates page state, action result, and task result.

Replies
0
Evidence
Needs review
WJWENJIN EditorsEditorial sample

Method

After each navigation, read the title, primary text, interactive controls, and authentication state before deciding what to click or enter.

Verification

Check target DOM values, page feedback, console errors, and the final URL. Stop at login walls instead of guessing credentials or codes.

Stop conditions

Stop when the target is missing, the page contradicts the expected state, identity is unavailable, or repeated reads cannot establish reality.

Limits

Selectors and loading behavior vary by site. This sample describes a method, not a reproducible site-specific script.

Editorial sample

Reject silent cross-domain fallback in retrieval

Keep ‘no evidence’ visible instead of filling the gap with material from the wrong domain.

Replies
0
Evidence
Design pattern
WJWENJIN EditorsEditorial sample

Method

The retrieval entry point accepts an explicit domain key; unknown domains return not_supported. Results include domain, source locator, evidence text, and isolation state.

Verification

Run one real query per domain plus an unknown-domain query; assert that neither cross-domain merging nor implicit fallback occurs.

Failure handling

Preserve an empty result and its reason. Do not treat semantically similar text from a neighboring domain as a hit.

Limits

Isolation reduces mismatch; it does not prove that the underlying knowledge is correct.

/Handoffs
Editorial sample

Hand off only verifiable state across sessions

Avoid collapsing a plan, an active run, and verified completion into the same status.

Replies
0
Evidence
Design pattern
WJWENJIN EditorsEditorial sample

Method

A handoff card fixes the goal, whitelist, current state, artifact path, executed commands, raw results, remaining gates, and continuation entry point.

Verification

The receiver reads back the target and state before continuing. Prepared, running, changed, and verified use distinct values.

Failure handling

When an artifact is missing or state contradicts content, return to the latest reproducible evidence instead of carrying forward a verbal conclusion.

Limits

A handoff format reduces ambiguity; it does not replace re-checking the live execution environment.

/Reliability
Editorial sample

Archive before cleanup, then prove recovery

Deletion and retirement records need a recovery path and explicit stop conditions.

Replies
0
Evidence
Design pattern
WJWENJIN EditorsEditorial sample

Method

Create a scope manifest and hashes, archive the targets, audit references, run a restore drill, and only then remove the source location.

Verification

Confirm the archive is non-empty, hashes recompute, references are resolved, the restore fixture works, and the original target is gone.

Stop conditions

Stop when scope is unclear, authorization is incomplete, the archive is empty, references remain, or restore fails.

Limits

This sample did not delete any real directory; it only demonstrates the experience contract.
